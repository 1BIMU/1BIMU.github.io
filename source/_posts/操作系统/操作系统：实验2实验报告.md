## 一、 实验目的  

本实验旨在深入理解 Linux (openEuler) 的虚拟内存管理机制。  

1. **理解虚拟内存组织**：掌握 VMA (Virtual Memory Area) 的概念以及虚拟内存与物理内存的映射关系。  
    
2. **掌握内存操作 API**：熟练使用 `mmap`, `munmap`, `mlock` 等系统调用控制进程的虚拟地址空间。  
    
3. **验证 Lazy Allocation**：通过实验观察“申请内存”与“实际分配物理页”的时间差，验证操作系统的按需分配策略。  
    
4. **掌握进程间通信 (IPC)**：学习使用 POSIX 共享内存 (`shm_open`) 和信号量 (`sem_t`) 实现多进程间的数据共享与同步。  
    

## 二、 实验要求及内容  

### 2.1 内存分配-跟踪双线程实验  

在一个进程内创建两个线程：  

- **分配线程 (Allocater)**：读取 `input.txt` 中的指令，执行内存分配、写入、锁定、释放等操作。  
    
- **跟踪线程 (Tracker)**：实时监控并打印当前进程的内存状态。**注意：本实验代码主要监控 `VmPeak` (虚拟内存峰值) 和 `VmHWM` (物理内存峰值)。**  
    
- **同步**：使用线程间信号量保证“执行一步，记录一步”。  
    

### 2.2 内存分配-跟踪双进程实验  

将上述功能拆分为两个独立的进程 `p1` 和 `p2`：  

- **P1 (Allocater)**：负责执行内存操作。  
    
- **P2 (Tracker)**：负责创建共享内存、初始化信号量，并监控 P1 的内存。**本实验改进了监控逻辑，实时监控 `VmSize` (当前虚拟内存) 和 `VmRSS` (当前物理内存)。**  
    
- **通信机制**：使用共享内存传递 P1 的 PID、当前操作类型和页数；使用共享内存中的信号量实现进程同步。

## 四、 实验原理与步骤  

### 4.1 核心机制：Lazy Allocation (懒惰分配)  

在 Linux 中，调用 `mmap` 申请内存时，内核仅在进程的 `mm_struct` 中创建了一个新的 VMA (虚拟内存区域)，**并不立即分配物理页**。此时虚拟内存增加，但物理内存不增加。 只有当程序首次写入该地址时，CPU 触发**缺页中断 (Page Fault)**，内核捕获中断并分配物理页帧，建立页表映射。此时物理内存才会增加。  

### 4.2 监控指标说明  

- **VmSize**: 进程当前使用的虚拟内存总量。  
- **VmRSS**: 进程当前占用的物理内存总量 (Resident Set Size)。  
- **VmPeak**: 进程运行过程中的虚拟内存峰值。  
- **VmHWM**: 进程运行过程中的物理内存峰值 (High Water Mark)。

### 4.4 关键代码修改  

为了获取更详细的数据，我修改了`memory_op.c`中的 `show_memory_usage` 函数，使其能同时捕捉四个指标：  

```c  
void show_memory_usage()  
{  
    FILE * fp;  
    char filename[32];  
    sprintf(filename, "/proc/%d/status", getpid());  
    fp = fopen (filename, "r");  
    char line[100];  
    
    while (fgets(line, sizeof line, fp) != NULL) {  
        // 筛选并打印这四个关键指标  
        if (strncmp(line, "VmPeak:", 7) == 0 ||  
            strncmp(line, "VmSize:", 7) == 0 ||  
            strncmp(line, "VmHWM:", 6) == 0 ||  
            strncmp(line, "VmRSS:", 6) == 0) {  
            printf("%s", line);  
        }  
    }  
    printf("----------\n");  
    fclose(fp);  
}  
```

**深度现象解析**：  

1. **为什么 VmSize 高达 150MB？** 实验 1 使用了 `pthread` 多线程。Linux 默认会为每个线程预分配大量的栈空间（Stack），这就是图中 `VmSize` 和 `VmPeak` 基数巨大的原因。  
    
2. **总量为什么不变**： 由于基数太大（150MB），我们分配的 50页（200KB）内存仅占总量的 0.1%，导致在右轴（虚拟内存）上几乎看不出变化。  
    
3. **物理内存验证**： 左轴（物理内存）清晰展示了 `write` 操作带来的 **160KB (40页)** 和 **128KB (30页)** 的阶梯式增长，验证了写时复制/分配机制。

**深度现象解析**：  

1. **清晰的“剪刀差”**： 由于 `mm-p1` 是独立进程，没有多线程栈的干扰，其初始虚拟内存仅 2.4MB。这使得每一次 `mmap` 操作（+200KB）都在图表上形成了清晰的向上跳变（蓝线），而此时绿线（物理内存）保持水平。这是 **Lazy Allocation** 最直观的证据。  
    
2. **HWM 的异常回落**： 观察数据发现，在最后一步 `munmap` 时，`VmHWM` 从 1588 降到了 1564。通常 High Water Mark 代表历史峰值不应下降。这表明在当前的 openEuler 内核实现中，HWM 可能被实现为了某种“滑动窗口峰值”或在特定释放操作下被重置，这是一个值得注意的系统特性  

## 六、 实验心得与体会  

**时间统计**：代码编写 4小时，上机调试 3小时。  

1. **多线程 vs 多进程的内存开销差异**： 通过对比两个实验的 `VmSize` 基数（150MB vs 2.5MB），我深刻体会到了多线程程序的隐性内存开销（线程栈）。这提示我在未来的系统设计中，如果对内存敏感，需要谨慎评估线程池的大小。  
    
2. **Bug 修复与代码健壮性**： 针对原代码存在的死锁问题（Tracker 无法退出），我通过在 Allocater 退出前增加 `sem_post` 信号进行了修复，保证了实验数据的完整采集。  
    
3. **全指标监控的意义**： 最初只监控 Peak/HWM 时，很难观察到 mmap 的效果。改为全指标监控后，不仅看到了物理内存的“懒惰”，还看到了虚拟内存的“承诺”，这让我明白了系统观测中“选择正确指标”的重要性。  

## 七、附录  
mm-p1实现：  
```c  
#include <stdio.h>  
#include <stdlib.h>  
#include <unistd.h>  
#include <sys/mman.h>  
#include <sys/stat.h>  
#include <fcntl.h>  
#include <string.h>  
#include <semaphore.h>  
#include "mm_share.h"  

int main() {  
    int pagesize = getpagesize();  
    int fd_shm;  
    struct shared_data *shared;  

    fd_shm = shm_open(SHM_NAME, O_RDWR, 0666);  
    if (fd_shm == -1) {  
        fprintf(stderr, "错误：无法打开共享内存。请先运行 ./mm-p2\n");  
        exit(1);  
    }  
    shared = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd_shm, 0);  
    if (shared == MAP_FAILED) {  
        perror("mmap shared failed");  
        exit(1);  
    }  

    shared->pid_alloc = getpid();  
    printf("Allocator (P1) 启动成功. PID: %d\n", shared->pid_alloc);  

    sem_post(&shared->sem_trac);  

    FILE *fp = fopen("input.txt", "r");  
    if (!fp) {  
        perror("无法打开 input.txt");  
        exit(1);  
    }  

    int oper, start, block, protection;  
    int base = 1 << 20;  
    char *region = NULL;  

    // 循环读取指令  
    while (fscanf(fp, "%d%d%d%d\n", &oper, &start, &block, &protection) != EOF) {  
        sem_wait(&shared->sem_alloc);  

        shared->oper = oper;  
        shared->pages = block;  
    
        void *target_addr = (void *)(long)(pagesize * (base + start));  
        shared->addr = target_addr;  

        if (oper == 0) { // mmap  
            region = mmap(target_addr, pagesize * block, PROT_READ|PROT_WRITE|PROT_EXEC, MAP_ANON|MAP_PRIVATE, 0, 0);  
            if (region == MAP_FAILED) perror("mmap failed");  
            else printf("[P1 操作] mmap: addr=%p, pages=%d\n", region, block);  
            shared->addr = region;  
        }  
        else if (oper == 1) { // write  
            if (region) {  
                for (int i = 0; i < pagesize * block; i++)  
                    memset((void*)((char*)region + i), 'a', 1);  
                printf("[P1 操作] write: addr=%p, pages=%d\n", region, block);  
            }  
        }  
        else if (oper == 2) { // mlock  
            mlock(target_addr, block * pagesize);  
            printf("[P1 操作] mlock\n");  
        }  
        else if (oper == 3) { // munlock  
            munlock(target_addr, block * pagesize);  
            printf("[P1 操作] munlock\n");  
        }  
        else if (oper == 4) { // munmap  
            munmap(target_addr, block * pagesize);  
            printf("[P1 操作] munmap\n");  
        }  

        sem_post(&shared->sem_trac);  
    }  

    sem_wait(&shared->sem_alloc);  
    shared->finished = 1;  
    sem_post(&shared->sem_trac);  

    fclose(fp);  
    return 0;  
}  
```

#ifndef MM_SHARE_H  
#define MM_SHARE_H  

#include <semaphore.h>  

struct shared_data {

    sem_t sem_trac;  
    int pid_alloc;  
    int oper;  
    void* addr;  
    int pages;  
    int finished;

#define SHM_NAME "/myshm_exp2"  
#define SHM_SIZE sizeof(struct shared_data)  

#endif
